# Уверенность по доказательствам, а не по ощущению {#ch7 data-short="Глава 7 · Уверенность по доказательствам"}

<div class="quote">
<div class="who"><div class="avatar">2–9</div><div class="name">Правило лестницы доказательств</div><div class="role">PAF Product Ops</div></div>
<div class="bubble">

«Нет ссылки — нет ступени. Уверенность не назначается мнением и не голосуется: она считывается с лестницы по самому сильному артефакту, который существует и открывается по ссылке».

</div>
</div>

Дата в квартальном плане обычно стоит на одном из трёх оснований: устное обещание смежника, демо на заглушках или проверка, сделанная до последнего релиза смежной системы. Все три выглядят в статусе одинаково — «согласовано», «работает», «проверено». Различие становится видно в последние две недели квартала, когда менять что-либо поздно.

Confidence Point (CP) — числовая мера основания обещания по шкале 2–9. CP ставки определяется тремя правилами: ступень по самому сильному артефакту, потолки по способу получения и минимум по критическим зависимостям. Сверху действует распад: проверка теряет силу по сроку годности объекта. Все четыре правила механические, поэтому CP можно пересчитать без автора — это и делает его пригодным для работы с ИИ-агентом.

Каркас фиксирован, формулировки ступеней под свой домен подбираются один раз в начале квартала и до его конца не меняются. Самая частая переоценка — 5 вместо 6: прогон на заглушках и тест против системы смежника в статусе одинаково называются «протестировано».

### Четыре вопроса, чтобы выставить ступень

Ступень выставляется по одному артефакту за четыре вопроса. Ответ на каждый может только понизить результат.

<div class="cards">
<div class="card"><span class="n">1</span><span class="t">Открывается ли артефакт по ссылке?</span><span class="d">Нет — запись идёт в журнал наблюдений и на CP не влияет</span></div>
<div class="card"><span class="n">2</span><span class="t">Автор — владелец объекта?</span><span class="d">Нет — это пересказ, потолок 2, сколько бы людей его ни повторили</span></div>
<div class="card"><span class="n">3</span><span class="t">Каким каналом получен?</span><span class="d">Устно, в личке или чате — потолок 3. Письмо, тикет, MR, прогон тестов — без потолка</span></div>
<div class="card"><span class="n">4</span><span class="t">Что проверено и на каком объёме?</span><span class="d">Ступень по таблице 1; объём записывается всегда: «50 транзакций», а не «работает»</span></div>
</div>

Два дополнительных потолка действуют поверх ответов. Если команду или систему видно реже раза в спринт, CP не выше 5. Если два источника расходятся, CP не выше 4, пока расхождение не снято: система не выбирает удобный источник, расхождение и есть неопределённость.

Ступень 6 по чужой системе не требует участия её владельца: тест против реального API делает своя команда. Подпись смежника нужна только там, где руками не проверить, — сроки, люди, юридические вопросы.

### Сквозной пример: расчёт CP одной ставки

Ставка: «Расчёты с внешним организатором работают к 15.11». Обещание уходит на квартальный обзор, поэтому действует гейт `commit` с порогом 6; решение принимается за две недели до срока — 01.11. Сегодня 14.10.

<table>
<thead><tr><th>Зависимость</th><th>Артефакт</th><th class="c">Ступень</th><th>Поправки</th><th class="c">CP</th></tr></thead>
<tbody>
<tr><td>API выплат финансовой системы</td><td>Письмо владельца: «API к 15.10, выплаты и возвраты»</td><td class="c">3</td><td>—</td><td class="c">3</td></tr>
<tr><td>Платёж на стенде партнёра</td><td>Прогон 50 транзакций против реального стенда</td><td class="c">6</td><td>Объём: 50 транзакций, без возвратов</td><td class="c">6</td></tr>
<tr><td>Схема фискальных данных</td><td>Сверка с документацией 63 дня назад</td><td class="c">5</td><td>Срок годности 21 день, просрочен трижды: −4</td><td class="c">2</td></tr>
<tr><td>Договор с организатором</td><td>Юрист сказал на созвоне «согласуем»</td><td class="c">2</td><td>Канал устный</td><td class="c">2</td></tr>
<tr><td colspan="4">Ставка: минимум по критическим зависимостям</td><td class="c">2</td></tr>
</tbody>
</table>

::: caption
Таблица 3. Расчёт CP ставки. Порог гейта — 6, до решения 18 дней
:::

::: thesis
Среднее по четырём зависимостям — 3,25, и ставка выглядит «в процессе». По правилу слабого звена её CP равен 2. Хуже того, две зависимости из четырёх стоят на ступени 2: одна из-за устного канала, другая из-за распада проверки, которая два месяца назад была сильной.
:::

Таблица сразу показывает, что делать. Пересверить схему — один день работы, и CP зависимости вернётся к 5, если схема не менялась. Письмо юриста поднимает договор до 3. API выплат — главное ограничение: после поставки 15.10 нужен тест против реальной системы, чтобы выйти на 6. Без него ставка не пройдёт гейт даже при идеальных остальных зависимостях.

В файле ставки это выглядит так:

```yaml
node_id: bet-raschety-organizator
gate: commit           # дата наружу, порог из gates.yaml
threshold: 6
due: 2026-11-15
cp: 2
cp_history: ["нед1:2", "нед3:3", "нед5:3", "нед6:2"]   # падение на нед6 — распад схемы
depends_on: [api-vyplaty, test-stend-partnera, fiscal-schema, dogovor-organizator]
non_critical: []       # исключить зависимость из минимума можно только с причиной
```

### Распад: проверка теряет силу по сроку годности

Срок годности назначается узлу знания по тому, как часто меняется сам объект, а не по типу документа.

<table>
<thead><tr><th>Частота изменений объекта</th><th class="c">Срок годности</th><th>Типичные объекты</th></tr></thead>
<tbody>
<tr><td>Высокая: чаще раза в месяц</td><td class="c">21 день</td><td>API и схемы данных активно развиваемых систем, состав команд</td></tr>
<tr><td>Средняя: раз в квартал</td><td class="c">42 дня</td><td>Процессы, приоритеты смежников, квартальные планы</td></tr>
<tr><td>Низкая</td><td class="c">90 дней</td><td>Договоры, юридические основания, стабильные контракты</td></tr>
<tr><td>Неизвестна</td><td class="c">21 день</td><td>Считается как высокая</td></tr>
</tbody>
</table>

::: caption
Таблица 4. Сроки годности знания
:::

Расчёт: `p = (сегодня − дата артефакта) / срок годности`. При `p < 1` ступень не теряется. Дальше `потеря = (p − 1) × 2` ступени, а действующая уверенность `= max(2, ступень − потеря)`. Узел со ступенью 6 и сроком 21 день через 63 дня имеет `p = 3`, теряет 4 ступени и стоит на 2.

Частота изменений определяется в таком порядке: история коммитов схемы, релизноуты и журнал инцидентов (около 20 минут); вопрос владельцу «как часто это менялось за полгода»; если данных нет — высокая. Ошибка несимметрична: завышенная частота стоит лишней перепроверки, заниженная — протухшего знания под датой квартала.

### Арифметика срока: видно ли срыв заранее

Значение CP на одну дату говорит меньше, чем темп его роста. Для ставки из примера: за шесть недель CP вырос с 2 до 3 и снова упал до 2. Нужно +4 ступени за 18 дней до решения. При историческом темпе +1 за четыре недели ставка не проходит гейт — и это видно 14.10, а не 01.11.

Для ставки из примера решение на 14.10: заказать тест API выплат на 16–17.10, пересверить схему до 15.10, запросить письмо юриста с датой ответа 20.10. Если 21.10 тест не пройден, дата 15.11 снимается, и наружу уходит дата проверки, а не срок.

### Что исполняет инструмент, а что держится на дисциплине

Ценность CP в том, что его нельзя подкрутить. Часть правил это гарантирует программно: в стартовом репозитории памяти агента повысить `cp` без нового источника нельзя — команда отклоняется.

### Калибровка: проверка самой лестницы

В конце квартала заявленный CP каждой ставки сравнивается с исходом. Правки вносятся только при достаточной статистике: не меньше трёх ставок на ступень, не меньше трёх изменений объекта за 45 дней наблюдения. Одна сорванная ставка ступень не порочит.

<div class="listbox">

- **Переоценка.** Из ставок с CP 8 к сроку дошла половина — ступени сдвигаются вниз, например демо перестаёт считаться за 4.
- **Слепая зона.** Сорвалось то, чего не было ни в одном списке зависимостей, — заводится недостающий узел.
- **Неверный распад.** Узел считался свежим, а объект успел измениться — его частота изменений повышается.

</div>

::: thesis
Итог для руководителя: CP ставки — это минимум по зависимостям после потолков и распада, и пересчитать его может кто угодно по тем же артефактам. Дата наружу даётся при CP не ниже порога гейта. Когда темп роста CP не дотягивает до порога, решение принимается в момент, когда это видно, — обычно за четыре–шесть недель до срока.
:::
