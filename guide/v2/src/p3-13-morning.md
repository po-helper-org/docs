# Утренний ритуал {#ch13 data-short="Глава 13. Утренний ритуал"}

Утро руководителя заканчивается договором на день. К концу ритуала команды синхронизированы, вчерашняя работа агента принята, план на неделю и на сегодня составлен, рутина отдана агентам. Ритуал занимает около 45 минут, из них на управление потоками уходит около 20.

### Шесть шагов

<table>
<thead><tr><th>Шаг</th><th class="c">Время</th><th>Что делает руководитель</th><th>Что делает агент</th></tr></thead>
<tbody>
<tr><td>1. Статус</td><td class="c">5–10 мин</td><td>Читает утренний статус и отмечает, что поднять на синхронизации</td><td>К утру собрал статус</td></tr>
<tr><td>2. Синхронизация</td><td class="c">15 мин</td><td>Дейлик с командой или синк с техлидами по красным строкам. Цитаты — в очередь</td><td>Подготовил вопросы к красным строкам, после встречи разбирает очередь</td></tr>
<tr><td>3. Приёмка</td><td class="c">5–10 мин</td><td>Принимает или возвращает вчерашние результаты агента, подтверждает изменения в памяти</td><td>Сдал результаты с пометкой «что не проверено»</td></tr>
<tr><td>4. План</td><td class="c">10 мин</td><td>План до конца недели от ставок и гейтов, из него — задачи на сегодня и список «не делаю»</td><td>Предложил черновик плана по уверенности, гейтам и сорванному вчера</td></tr>
<tr><td>5. Задачи агентам</td><td class="c">5 мин</td><td>Отдаёт рутину из плана в формате из главы 8</td><td>Отвечает «Договорились»</td></tr>
<tr><td>6. Исполнение</td><td class="c">день</td><td>Решения, разговоры, последняя миля по результатам агента</td><td>Делает рутину, прерывает только по трём поводам</td></tr>
</tbody>
</table>

::: caption
Таблица 1. Шаги утреннего ритуала
:::

Порядок задан зависимостями между шагами. Статус читается до синхронизации, иначе встреча снова превращается в пересказ. Синхронизация идёт до плана, потому что ответы техлидов меняют приоритеты. Приёмка идёт до плана: принятая работа освобождает ёмкость, возвращённая попадает в план. Задачи агентам ставятся после плана, чтобы агент получил рутину из принятого плана.

Когда команд больше двух и у них есть техлиды, руководитель не ходит на дейлики команд. Вместо них одна синхронизация с техлидами на 15 минут по красным строкам. Потоки без красного отмечаются одной фразой «в норме». Когда процесс устоится, синхронизация сжимается до двух-трёх раз в неделю, а чтение статуса остаётся ежедневным.

### Утренний статус: три отчёта

<table>
<thead><tr><th>Отчёт</th><th>Что в нём</th></tr></thead>
<tbody>
<tr><td>За команду</td><td>Что подтверждено вчера, со ссылкой и объёмом. Что команда проверяет сегодня. Где нужна помощь и от кого. Молчание смежника — тоже строка</td></tr>
<tr><td>За агента</td><td>Первой строкой — что руководитель должен сделать, чтобы агент продолжил. Что агент сделал вчера и что это сняло с руководителя. Что сделает сегодня. Что ждёт подтверждения записи в память</td></tr>
<tr><td>За стратегию</td><td>Движение уверенности по ставкам. Что решить: уверенность ниже порога, но время есть. Что эскалировать: по правилу гейта не успевает. Что протухло и где тишина. У каждого риска — дата первого появления в статусе</td></tr>
</tbody>
</table>

::: caption
Таблица 2. Состав утреннего статуса
:::

Статус пишется подтверждениями. «Провели синк с партнёром» в него не попадает. «Прогнали 50 транзакций на стенде партнёра, ступень 6, ссылка» попадает. Проверка строки: если её убрать, изменится ли чья-то уверенность или чьё-то действие сегодня? Если нет, строку убирают.

Дата первого появления риска нужна для доказательства управляемости в конце квартала (глава 15). По истории статусов видно, за сколько недель до срока риск заметили и что с ним сделали.

### Данные собирает скрипт

Статус надёжен, только если данные к нему собираются по расписанию без участия модели, а модель пишет текст по готовому снимку данных.

<table>
<thead><tr><th>Время</th><th>Что происходит</th></tr></thead>
<tbody>
<tr><td>07:30</td><td>Скрипты снимают данные из трекера, календаря, очереди, памяти</td></tr>
<tr><td>08:00</td><td>Сводка календаря, пересмотр списков обещаний</td></tr>
<tr><td>08:15</td><td>Утренние статусы по потокам</td></tr>
<tr><td>08:30</td><td>Сводный статус руководителя</td></tr>
<tr><td>09:30–10:15</td><td>Ритуал</td></tr>
<tr><td>13:00, 18:00</td><td>Пакеты середины и конца дня</td></tr>
</tbody>
</table>

::: caption
Таблица 3. Расписание сборки. В первый квартал хватает запуска агента вручную в 09:20
:::

Если источник недоступен, в статусе одна строка: «Срез: данные до 07:30, трекер недоступен». В риски по целям сбой не попадает, владельцу агента уходит отдельный алерт. Пустой результат без такой строки выглядит как спокойный день и вводит в заблуждение.

### Пример: среда, 14 октября

<table>
<thead><tr><th>Время</th><th>Что происходит</th></tr></thead>
<tbody>
<tr><td>09:30</td><td>Статус. Команда: 12.10 прогнали 50 транзакций на стенде партнёра, ступень 6; API выплат не поставлен, поставка обещана 15.10. Агент: нужно от руководителя — переслать в очередь письмо владельца API выплат с датой поставки. Стратегия: ставка «Расчёты» стоит на 2, проверке фискальной схемы 63 дня, срок годности 21 день; по правилу гейта ставка не успевает к решению 30.10</td></tr>
<tr><td>09:40</td><td>Синк с четырьмя техлидами. Платформа, собственные продажи и обслуживание — в норме. Техлид подключения передаёт слова техлида партнёра: «возвраты на стенде работают». Цитата уходит в очередь, ступень 2</td></tr>
<tr><td>09:55</td><td>Приёмка: отчёт по спринту принят, черновик запроса партнёру возвращён с правкой, две записи в память подтверждены</td></tr>
<tr><td>10:00</td><td>План недели: пересверка схемы до 15.10, тест API 16.10, прогон возвратов до 20.10. Сегодня — три задачи. Не делаю — переработку шаблона требований</td></tr>
<tr><td>10:10</td><td>Задачи агентам: письмо владельцу API выплат (глава 8), запрос партнёру на прогон возвратов, сводка дня к 17:30</td></tr>
<tr><td>10:15</td><td>Агент ответил «Договорились». Дальше — исполнение</td></tr>
</tbody>
</table>

::: caption
Таблица 4. Ритуал руководителя «Мероприятий» 14.10
:::

::: thesis
За 45 минут руководитель увидел падение главной ставки, понял причину по одной строке статуса, составил план из трёх артефактов и отдал агентам три задачи. До 30.10 остаётся 16 дней, и план на них готов в первый же день, когда риск появился в статусе.
:::

### Где ритуал ломается

<table>
<thead><tr><th>Признак</th><th>Причина</th><th>Что делать</th></tr></thead>
<tbody>
<tr><td>На синхронизации пересказывают состояние дел</td><td>Статус не прочитан к встрече</td><td>Начинать встречу с красных строк статуса</td></tr>
<tr><td>Агент делает новое поверх непринятого</td><td>План составлен до приёмки</td><td>Вернуть приёмку перед планом</td></tr>
<tr><td>Приёмка превращается в переделку</td><td>У задач нет поля «как проверим»</td><td>Не ставить задачу без него</td></tr>
<tr><td>Ритуал три дня подряд длится больше часа</td><td>Статус или синхронизация перегружены</td><td>Урезать то, что руководитель пролистывает</td></tr>
</tbody>
</table>

::: caption
Таблица 5. Сбои ритуала
:::

Первые три недели ритуал калибруется по замерам из журнала: минуты руководителя на чтение статуса и ответ (цель — не больше 15), доля пунктов с ответом за день, доля строк-подтверждений, доля полезных пунктов в отчёте агента о себе, запас дней между первым появлением риска и датой гейта. Тему, которую руководитель систематически пропускает, из статуса убирают. Строку «Срез» оставляют всегда: без неё пустой день не отличить от сломанного агента.
