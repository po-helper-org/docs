# Память агента {#ch4 data-short="Глава 4. Память агента"}

Агент отвечает настолько точно, насколько проверяем контекст, который ему дали. Пересказ переписки или выгрузка из головы руководителя дают ответы, которые звучат уверенно и не опираются ни на что. Поэтому работа с агентами начинается с памяти: набора файлов, где у каждого утверждения есть автор, канал, дата и ссылка на источник.

В PAF такая память называется Нексусом, а агент с правилами работы с ней — Кортексом [1]. Порядок их создания важен. Сначала собирают проверяемый контекст, потом подключают агента. Агент без проверяемого контекста ускоряет перенос слухов.

### Почему файлы под git

Память хранится в обычных текстовых файлах в репозитории git. Таблица или вики дают то же содержание, но git бесплатно добавляет три свойства, которые иначе пришлось бы строить.

<table>
<thead><tr><th>Что нужно памяти</th><th>Чем это даёт git</th></tr></thead>
<tbody>
<tr><td>Кто и когда записал утверждение</td><td>Автор и дата каждого изменения</td></tr>
<tr><td>Когда последний раз проверяли узел</td><td>Дата последнего изменения файла</td></tr>
<tr><td>Как менялась уверенность по ставке</td><td>История изменений файла ставки</td></tr>
<tr><td>Защита от правки задним числом</td><td>Подписи коммитов, защита веток и владельцы файлов — с уровня 2, когда пишут несколько человек</td></tr>
</tbody>
</table>

::: caption
Таблица 1. Свойства памяти и механизмы git
:::

ИИ-агенты, которые работают с репозиторием, например Claude Code, читают и меняют такие файлы напрямую. Отчёты из памяти не хранятся, а генерируются по запросу.

### Шесть слоёв

<thead><tr><th>Слой</th><th>Что лежит</th><th>Правило записи</th></tr></thead>
<tbody>

<tr><td><code>evidence/</code></td><td>Артефакты: письма, прогоны, протоколы, выгрузки</td><td>Только добавление, файлы не меняются</td></tr>

<tr><td><code>bets/</code></td><td>Ставки: порог, дата, зависимости, уверенность</td><td>Уверенность пересчитывает инструмент</td></tr>

Таблица 2. Слои памяти. В стартовом шаблоне poh-cortex [2] те же слои лежат в папке GROUND

Знание движется в одну сторону. Из потока — чатов, почты, созвонов — агент отбирает кандидатов и складывает их в очередь. Человек решает, какой кандидат становится артефактом. Из артефактов собираются узлы, из узлов выводится уверенность по ставкам. Обратного движения нет: ставка не может изменить артефакт, а агент не может записать узел без подтверждения.

### Что хранить: объекты решений руководителя

В исходном PAF нексусы описывают рынок, продукт, систему роста, компанию и операционную модель. У руководителя в корпорации объекты решений другие, и память собирается под них.

<table>
<thead><tr><th>Нексус</th><th>Что внутри</th><th>Какое решение он защищает</th></tr></thead>
<tbody>
<tr><td>Оргструктура</td><td>Кто владеет какой системой, кто на что влияет</td><td>Кому писать, чтобы вопрос сдвинулся</td></tr>
<tr><td>Операционная модель</td><td>Ритуалы, гейты, чьё согласие нужно</td><td>Когда ставить вопрос, чтобы его решили</td></tr>
<tr><td>IT-ландшафт</td><td>Системы, контракты, интеграции, SLA, версии схем</td><td>Можно ли обещать срок по интеграции</td></tr>
<tr><td>Бизнес-процессы</td><td>Как проходят заказ, оплата, возврат, поддержка</td><td>Не забыть процесс, из-за которого сорвётся квартал</td></tr>
<tr><td>Финансы</td><td>Юнит-экономика, бюджет, что считается эффектом</td><td>Чем обосновать приоритет</td></tr>
<tr><td>Стратегия</td><td>Цели, ставки и история их изменений</td><td>Что делать, если стратегия поменялась</td></tr>
<tr><td>Эксперименты</td><td>Что пробовали и чем закончилось</td><td>Не проверять дважды одно и то же</td></tr>
<tr><td>Внешние зависимости</td><td>Владельцы, каналы, обещания, скорость ответа</td><td>Давать ли дату по чужой зоне</td></tr>
</tbody>
</table>

::: caption
Таблица 3. Восемь объектов, по которым руководитель принимает решения
:::

Узел заводится, когда из-за его незнания руководитель уже принял плохое решение. Три–четыре нексуса на первый квартал достаточно. Восемь на старте превращают память в справочник, который никто не открывает. Нексус без читателей вреднее отсутствующего: он создаёт ощущение, что знание есть.

### Пример: память направления «Мероприятия»

На старте квартала руководитель заводит три нексуса и пять ставок под KR «Подключены 3 внешних организатора».

```text
memory/
  rules/       ladder.md  gates.md  decay.md
  nexus/
    it-landscape/   sistema-raschetov.md  api-vyplaty.md  fiscal-schema.md
                    test-stend-partnera.md  vozvraty-stend-partnera.md
    dependencies/   finansy-vyplaty.md  partner-tehlid.md
    org/            vladeltsy-sistem.md
  bets/        bet-katalog.md  bet-inventar.md  bet-raschety-organizator.md
               bet-postprodazha.md  bet-dogovory.md
  evidence/    2026-09-17-petrov-obyem.md  2026-10-12-progon-stend-50.md
  log/         2026-10.md
  decisions/   2026-10-14-plan-raschety.md
  inbox.md
```

Нексусов рынка, сегментов и конкурентов в памяти нет. Решения квартала зависят от интеграций и смежников, поэтому память начинается с них.

### Узел знания

Узел — файл с шапкой и текстом. Шапка содержит поля, по которым инструмент считает свежесть и уверенность.

```yaml
node_id: api-vyplaty
node_type: dependency
owner: финансы, владелец системы выплат
channel: email                # канал, по которому приходят подтверждения
change_rate: high             # меняется чаще раза в месяц, срок годности 21 день
updated: 2026-10-16           # дата самого артефакта, а не записи
cp: 6
sources: [2026-10-16-test-api-vyplaty.md]
status: accepted              # запись агента — draft, пока человек её не примет
```

У узла типа «зависимость» обязательны владелец и канал. Пустой список источников считается браком и не проходит проверку целостности.

::: thesis
Качество памяти измеряется спелостью — произведением полноты и актуальности. Полнота показывает, какая часть нужных полей заполнена. Актуальность падает по сроку годности узла. Узел с высокой уверенностью и просроченной проверкой тянет вниз все ставки, которые на нём стоят.
:::
