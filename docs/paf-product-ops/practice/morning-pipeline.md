# Утренний конвейер и ИИ-аналитика

[Шаг 3-бис](../mechanics/step-3-bis-morning-status.md) и [Шаг 3-тер](../mechanics/step-3-ter-morning-ritual.md) описывают утренний статус и ритуал PO. Практика показала, что они работают, только если данные собираются **по расписанию без участия модели**, а итог умещается в одну строку.

!!! abstract "Где реализовано"
    [`poh-po-day`](https://github.com/po-helper-org/poh-po-day) (процесс дня PO, SPEC и 46 пользовательских историй — пока в незамёрженном PR), [`poh-morning-status`](https://github.com/po-helper-org/poh-morning-status) (навык утреннего брифа), [`poh-widget-inbox`](https://github.com/po-helper-org/poh-widget-inbox) (ИИ-аналитика, ADR 0007), [`poh-dev-daily`](https://github.com/po-helper-org/poh-dev-daily) (дейлик разработчика).

## Принцип: считает код, собирают агенты, решает человек

Данные собирает скрипт, а не модель; отчёт пишется только из снимка данных. Такой снимок кэшируется на час; бюджет навыка — 4–6 вызовов вместо двух десятков шагов; файлы отчёта пишутся по мере готовности (устойчивость к обрыву). Уверенность и ступени считает инструмент, а не формулировка модели в тексте статуса. Агенты собирают в очередь и готовят черновики, запись в знание — одним диффом после «да».

## Расписание

Порядок запусков важен: аналитика обещаний — до утренних статусов.

| Время (МСК) | Что происходит |
|---|---|
| 07:30 | Снимки сборщиков (без модели) |
| 08:00 | Календарная сводка дня; ИИ-аналитика обещаний |
| 08:15 | Утренние статусы PO-агентов по потокам |
| 08:30 | Сводный статус; автосбор снимка спринтов по будням; выпуск отчёта по ленте (с повторной проверкой в 09:15 и 10:15 без модели) |
| 09:00–09:50 | Ритуал PO: статус → синк с техлидами → приёмка → план «неделя → сегодня» → задачи агентам → «Договорились» |
| 13:00, 18:00 | Пакеты середины и конца дня |
| До 21:00, ночь | Ночной пакет: утвердить вечером; ночью только чтение и черновики |
| Пн 06:00 | Недельный разбор агента выравнивания трекера |

Цель ритуала — не больше 45 минут утром и 15 минут на чтение статуса и ответ; метрики калибруются за три недели.

## Формат брифа

Бриф — не пересказ каналов, а «что изменилось так, что меняет план». Три класса сигналов: **ждут тебя**; **сдвиг или блокер**; **факт к цели**. Остальное — числом («Прочее: 47 сообщений в 6 чатах»). Лимиты: задачи ≤ 7, ретро ≤ 8, «нужны решения» ≤ 5; строка из четырёх чисел (просрочено · сегодня · рисков без владельца · закрыто вчера). Просроченное обязательно разрешается: сделать, перенести или закрыть. Бриф, выросший до двух экранов, функцию не выполнил — поправка владельца к первой версии аналитики: «слишком перегружено», теперь итог — одна строка и чат.

## «Срез вместо шума»

Недоступный источник — одна строка «данные до …, недоступно: …» и отдельный алерт владельцу агента; в риски по целям он не попадает. Пробел виден как `[НЕТ ДАННЫХ: причина]`, а не заполняется догадкой. Урок миграции: инструмент с «молчаливым нулём» («реестр пуст», код 0) хуже громкой ошибки — молчаливый ноль выглядит как валидный результат.

## «Договорились» и «Додумал сам»

Каждый агент в ответ на решения PO пишет: что беру и к какому сроку; что жду от PO; что **додумал сам**. Последняя тема обязательна даже при содержимом «ничего»: это допущения, с которыми агент пойдёт дальше без вопроса. Нет ответа за 10 минут — Штаб поднимает строкой. Прерывать PO днём допустимо по трём поводам: уверенность пересекла ворота вниз; обязательство сорвётся и разблокировать может только PO; нужно внешнее действие PO. Остальное — в два пакета.

## ИИ-аналитика обещаний

Раз в сутки агент пересматривает оба списка обещаний ([обещания](promises.md)) и выносит решения пяти групп.

| Решение | Применяется |
|---|---|
| Завершено · Неактуально · Сдвинуть срок | Само — если уверенность высокая и доказательство проверено |
| Нужно добавить · Объединить · Сделать подзадачей | Всегда по ✅ |
| Напомнить | Текст для копирования: людям пишет человек |

Как это устроено:

- Сбор — без модели: открытые обещания, 40 последних заметок, задачи доски за 14 дней, встречи на неделю вокруг, отклонённые ранее решения (14 дней не предлагать то же).
- Модель отвечает структурой: решение, уверенность, причина, доказательства.
- **Код проверяет:** обещание существует; цитата дословно есть в источнике (выдуманная цитата отправляет решение «ждать ✅»); дата ISO; ключ Jira корректен.
- Ограничители: не больше 10 самостоятельных действий за прогон; обещание, которое PO правил за последние 24 часа, не трогается; одно решение на обещание; «Отменить» действует сутки; журнал «что, когда, кем, прежний срок».
- Прогон ≈ 8,5 минуты на ~50 обещаний.

Честное ограничение из ADR: решения по Jira и ленте код проверить не может — только вид ссылки. Поэтому журнал и отмена обязательны. И спорная точка с принципом «уверенность считает только детерминированный инструмент»: здесь уровень «высокая» называет модель, а код подтверждает цитату. Практика трактует это как допустимую ступень **с компенсаторами**: журнал, окно отмены, лимит действий, память отказов.

## Дейлик разработчика

Разработчик рассказывает свободным текстом; агент сверяет рассказ с Jira и git, показывает план правок и после одного «да» меняет статусы и комментарии. Git подтверждает или противоречит, но статус не меняет; факт без следов остаётся «со слов». Вчерашние «план» и «блокеры» становятся обещаниями на сегодня. «Хвосты»: обещание без упоминания, блокер без упоминания, задача «в работе» без обновлений 3+ рабочих дня, работа без ключа Jira. Не больше трёх вопросов, с вариантом по умолчанию; переход берётся из списка допустимых переходов Jira, а не угадывается. Это конкретизация [Шага 3](../mechanics/step-3-daily-rhythm.md) для разработчика.
