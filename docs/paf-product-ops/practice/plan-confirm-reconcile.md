# План, подтверждение, запись, сверка

Методология требует, чтобы агент «записывал после подтверждения человека» ([П9](../playbook/p9-agent-team.md)). Практика превратила это в повторяемый конвейер и добавила то, чего не было в тексте: проверку после записи, критика плана и эталонные наборы для проверки самого агента.

!!! abstract "Где реализовано"
    [`poh-sprint-agent`](https://github.com/po-helper-org/poh-sprint-agent) (чат ИИ-агента рядом с отчётом спринта), ADR 0001, 0003–0007. Точки входа — виджеты [`poh-widget-sprint-observe`](https://github.com/po-helper-org/poh-widget-sprint-observe) и [`poh-widget-sprint-business`](https://github.com/po-helper-org/poh-widget-sprint-business). Зрелость: основное ядро в эксплуатации с 12–15 октября 2026.

## Конвейер

```text
замечания техлида/PO → агент → план действий → критик → человек отмечает ✅
        → сервис пишет в трекер → сверка → актуализация отчёта
```

1. **Агент без доступа на запись.** Данные — снимок отчёта в инструкции; профиль без Jira-инструментов, без мессенджера и без памяти.
2. **План проверяет код.** Белый список действий (создать историю, задачу, подзадачу, комментарий, сменить статус, исполнителя, связь); ключи задач — только из снимка и проектов команды.
3. **Пишет сервис, а не модель.** Через API виджета Jira; повтор не выполняется (таймаут не даёт дубль); ошибка одного пункта не останавливает остальные. Комментарии подписаны «подтвердил(а): имя».
4. **Сверка после записи.** Сервис перечитывает задачу: «в Jira сходится» или «расходится».
5. **Актуализация отчёта.**

Паттерн известен как «прерывание для одобрения» (LangGraph `interrupt()`, `needsApproval` в SDK агентов): право записи у кода, а не у модели.

## Гейт — это диалог

Единичное «да/нет» в практике оказалось слишком грубым. Агент ведёт **раунды вопросов**: «1 из N», 1–4 вопроса за раунд, 2–4 варианта с пометкой «рекомендую» и возможностью дать свой ответ. Он шлёт блок вопросов и ждёт в статусе «на приёмке» (не «заблокирован»: у Hermes на втором блоке задача уходит во «Входящие»). Ответ — комментарий и возврат из приёмки. Раундов сколько нужно. Сдача тоже идёт через приёмку.

Решение по каждому замечанию видно владельцу: в плане · уже так · вопрос · не про Jira. Это сочетается с правилом методологии «не больше двух-трёх вопросов за встречу» ([П6-бис](../playbook/p6-bis-information-contract.md)).

## Критик плана

Второй агент с другим доступом (Jira только на чтение) до подтверждения помечает пункты плана: «верно» · «сомнение» · «лишнее» (лишнее по умолчанию не отмечено) и называет упущенное. Это аналог питчинга доверия: **атаку на аргументы делает отдельный агент с другими правами**. Сбой критика не мешает подтверждению; цена — 30–90 секунд на ход.

## Обучение агента без «самообучения»

Методология предупреждает: самообучающиеся агенты дрейфуют ([П9](../playbook/p9-agent-team.md)). Практика пошла дальше — вместо запрета предложила управляемое улучшение.

| Элемент | Как устроено |
|---|---|
| Знание — навык | Методичка в репозитории без имён; справочники команд и разборы — в локальном git на сервере, без удалённой копии (там имена людей). Ставится в режиме «только чтение + закрепление версии»; установщик сообщает о дрейфе файлов |
| Журнал разборов | Построчно: замечания → план → критик → подтверждение или отказ → шаги → итог → оценка 👍/👎 с «почему». Оценка — главный сигнал |
| Эталоны | Замечания + допустимые решения + нужные и запрещённые правки + «не больше N правок на задачу». Проверка гоняет агента в режиме «только план» (трекер не меняется), оценка от 0 до 1, сравнение версий навыка |
| Недельный разбор | По таймеру раз в неделю: сводка журнала (без модели), черновики эталонов, предложения правок в виде диффа, прогон эталонов. Итог — одна задача во «Входящих» без исполнителя; неделя без замечаний и оценок — без задачи |
| Правило | **Знание меняется только после «да» владельца** |

Отвергнуто: встроенное самообучение (закрепляет ошибки без проверки), память из пары тысяч знаков, оптимизатор промптов (нужно хотя бы 30–50 эталонов), графовые движки памяти. Базовая диагностика на 24 реальных замечаниях: 17 из 19 правок были просто комментариями; закрытые задачи комментировались как живые; два замечания к одной задаче давали противоречащие комментарии. Именно такие слабости ловит эталонный набор.

## Что взять в свою практику

- Записывает сервис по белому списку, а не модель; после записи — сверка.
- Критик с другими правами перед подтверждением.
- Эталонный набор и недельный разбор для **самого агента** — это калибровка ([Шаг 9](../mechanics/step-9-calibration.md)) поведения, а не только ступеней CP.
- Правила агента — версионируемый навык, меняет человек.
