    ЧАСТЬ I. СУТЬ ТРАНСФОРМАЦИИ¶

    PAF отвечает на два c-level вопроса [S1]:

    1. Почему продуктовый подход НЕ даёт бизнес-результата? — потому что компаниям «продали» методологии разработки (Scrum, Kanban) как панацею от бизнес-проблем. Процесс разработки ≠ процесс развития продукта. Scrum оптимизирует потери производства, а развитие продукта отвечает на другой вопрос: как создать продукт с максимальным возвратом монетизируемой ценности на инвестиции (NPV) [S1].
    2. Каким должно быть управление продуктами в эпоху ИИ? — когда практически все задачи менеджера могут быть ИИзированы. ИИ = disruptive-технология раз в сто лет. Discovery решается почти мгновенно, часть задач полностью делегируется [S1, S2].

    Главный тезис [S2]: в эпоху ИИ конкуренция смещается с продуктов на контекст и модель управления им. «У кого лучше собран контекст продукта и реализована ИИзация работы с ним — тот и будет лидером на рынке».

    Что это значит для библиотеки RB-STEP. Библиотека RB-STEP-1 … RB-STEP-8 — это сильная, добротная реализация классического Product Discovery (Customer Development, JTBD, Lean, AARRR, MVP по Бланку). Но почти на каждом этапе она: - хранит контекст как разрозненные документы (а не живой Нексус-двойник); - предполагает ручную работу (а не работу через Кортекс); - мыслит списками/приоритизацией/беклогом (а не Банчем в моменте); - оптимизирует скорость/потери (а не риски через Confidence Point); - оперирует LTV/CAC/EBITDA как самоцелью (а не NPV/mNSM как возвратом монетизируемой ценности); - описывает процесс как линейный каскад с каденциями (а не асинхронный event-based цикл Product Sprint); - использует роли «продакт-менеджер / маркетолог / SDR» (а не AI-Native роли).

    Reformation = переписать каждый RB-STEP как AI-native инструкцию для Инженера Продукта нового поколения, сохранив методологическую силу классики, но заменив операционную модель.

    Инструкции нового поколения (N.M instruction) пишутся не для классического Product Owner/Manager, а для Инженера Продукта (Product Engineer) — роли, которая управляет развитием продукта через Нексус посредством Кортекса [S1, S2].

    Параметр Классический PO (Scrum-эпоха) Инженер Продукта нового поколения (PAF) Источник
    Базовый артефакт Беклог (накопительный список) Банч (в моменте, из текущего состояния Нексуса) [S1]
    Объект управления Поток задач в разработку Нексусы (рынок/продукт/рост/…) [S1]
    Ключевая метрика процесса Скорость / story points / потери Confidence Point (риски) [S1]
    Бизнес-метрика velocity, выручка, DAU NPV, mNSM (+ COGS токенов для AI-продуктов) [S1, S2]
    Инструмент работы с продуктом Вручную (Sheets/Notion/Jira/Figma) Через Кортекс (агенты/RAG/промпты) [S1]
    Способ принятия решений Приоритизация списка задач Скаутинг возможностей и угроз [S1] Принцип 5
    Знания Разрозненные документы Цифровой профиль продукта (единая точка) [S2]
    Ритм работы Каденции (спринты, PI) Event-based / Kanban [S1]
    Компетенции T-shaped Comb-shaped (гребёнка за счёт Кортекса) [S2]
    Команда Scrum-team (7±2) Pod (может быть из 1 человека) [S1, S2]
    Критический навык Процессная дисциплина Метапознание (валидация ИИ) [S2] III.4
    Bottleneck системы Discovery / разработка Дистрибуция (последняя миля) [S2] III.5 (Голдратт)

    Ключевой фильтр [S2]: рост качества от ИИ — только при достаточном метапознании. Junior без метапознания + ИИ = нулевой прирост. Компетентный, но забивший на верификацию = «убедительные, но неверные» результаты (Harvard × BCG). Поэтому каждая инструкция нового поколения содержит явные чекпоинты метапознания и анти-workslop гейты.

    ЧАСТЬ IV. 8 СКВОЗНЫХ ТРАНСФОРМАЦИЙ (применимы ко всем этапам)¶

    Соглашения об именовании¶

    • Физическая структура: по подкаталогам на стадию (зеркалит источник RB-STEP-*, исключает коллизию номеров — у STEP-1 внутренняя нумерация 1.x/2.x/…/6.x пересекается с нумерацией STEPs 2–8).
    • Содержимое каждого N.M instruction: Цель в PAF-оптике · Роль (Product Engineer / …) · Что делает Кортекс-агент · Что делает человек (метапознание) · Артефакт = узлы Нексуса · CP-гейт · Связь с 3PL · Анти-workslop чекпоинт · Маппинг к Skill Map/профстандарту · Связь с исходным RB-STEP-N/N.M (преемственность методов).
    • Терминология: строго по [[sa_documentation/naming_conventions|naming_conventions.md]] (запрещённые синонимы: Беклог→Банч, PM→Product Engineer, приоритизация→скаутинг, потери→риски, T-shaped→Comb-shaped, «документация»→цифровой профиль, метрики разработки→mNSM/NPV/CP).
    • Альтернатива (плоская структура): если предпочтительнее единый список без подкаталогов, использовать схему N.M где N=стадия, M=подшаг по порядку (1.1–1.18 для STEP-1, 2.1–2.7, 3.1–3.6, …). Решение за владельцем.

    ЧАСТЬ VII. МОДЕЛЬ ЗРЕЛОСТИ КОРТЕКСА (последовательность внедрения)¶

    Трансформация — не «всё сразу». Кортекс разворачивается по 3 фазам по объекту ИИзации [S1] Часть VII:

    Фаза Объект ИИзации Что появляется в инструкциях
    1 Отдельные задачи Промпт-шаблоны (генерация гипотез, скоринг, разбор интервью). Кортекс = ассистент.
    2 Процессы работы команд RAG по Нексусам + специализированные агенты (Nexus-Builder, Bunch Architect, Segmenter, NPV Scorer…). Кортекс = проводник.
    3 Процессы всей компании Сквозной event-based Кортекс: агенты обновляют Нексусы событийно, CP пересчитывается автоматически, осознанный отказ — gate.

    В каждой фазе — 3 уровня процессов (стратегический / операционный / отдельной команды) [S1]. Миссия Product Ops — двигать команду по этой модели [S2].

    Рекомендуемая последовательность внедрения по этапам: 1. Сначала Нексус, потом Кортекс [S1] Часть IX — без спелого контекста Кортекс усиливает мусор. Поэтому Phase-0 любой инструкции = построение Нексуса стадии. 2. STEP-1 (58%) — ближайший к PAF; поднять Кортекс с фазы 1→2 (Bunch Architect, Nexus-Builder), добавить NPV и метапознание. 3. STEP-4 (42%) — добавить mNSM (монетизируемость NSM) и Кортекс-агентов; наивысший ROI. 4. STEP-2 (18%) — самый большой разрыв; рефакторить артефакт 2.5 в Нексус потребителя + Transcript Coder. 5. STEP-3/5/6/7/8 — агенты и Нексусы по приоритету дистрибуции-bottleneck (6, 8) и финмодели-NPV (5).

    ЧАСТЬ IX. КРИТЕРИИ УСПЕХА ТРАНСФОРМАЦИИ¶

    Трансформация этапа считается завершённой, когда: - ✅ Каждый N.M instruction ведёт Инженера Продукта (не PM) через Кортекс над Нексусом. - ✅ Результат этапа = узлы Нексуса с метрикой Context Ripeness, а не разрозненный документ. - ✅ Решения принимаются через Confidence Point (gate) с оценкой стоимости риска, а не через приоритизацию/чекбокс. - ✅ Метрики этапа выражены через mNSM / NPV (+ COGS токенов для AI-продуктов), а не vanity. - ✅ Каждый Кортекс-агент имеет метапознание-чекпоинт и анти-workslop гейт. - ✅ Этап встроен в цикл Product Sprint (Progress Pulse … Harvesting) и привязан к 3PL. - ✅ Указан маппинг к Skill Map (6×3) и профстандарту 06.012 (A/B/C/D).
